# Simplified Technical English profile

## Purpose

This page defines the writing rules for the technical documents in
`docs/technical`. The rules follow ASD-STE100 Simplified Technical English.
The standard has a copyright. This page records the subset that Starforge
applies and the project dictionary.

Read this page before you add or change a technical document.

## Scope

The rules apply to all Markdown files under `docs/technical`.

The rules do not apply to code comments, commit messages, or the documents
under `docs/admin`, `docs/user`, and `docs/format`. Those documents can keep
their current style.

## Sentence rules

- Write one instruction in each sentence.
- Limit an instruction to 20 words.
- Limit a descriptive sentence to 25 words.
- Write the condition before the action.
- Put one topic in each paragraph.
- Limit a paragraph to 6 sentences.
- Use the active voice.
- Use the imperative for an instruction.
- Do not use parentheses in prose. Write a separate sentence.
- Do not use semicolons.
- Do not use em dashes.

## Verb rules

- Use the simple present, simple past, or simple future.
- Use the imperative for an instruction.
- Do not use the modal verbs `should`, `would`, `could`, `might`, `may`,
  or `shall`. The checker rejects them.
- Use `must` for a requirement.
- Use `can` for a capability or a permission.
- Do not use the progressive form. Write "the server stores the record",
  not `the server is storing the record`.
- Do not use contractions.

## Word rules

- Use one word for one concept. The glossary gives the approved terms.
- Use the approved term from the project dictionary.
- Do not use Latin abbreviations.
- Do not use the first person plural.
- Use American spelling.
- Remove words that add no meaning.

## Noun rules

- Limit a noun cluster to 3 words.
- Use articles.
- Do not use a noun as a verb.

## Procedures

- Start each step with an imperative verb.
- Give the condition before the command.
- Give the expected result after the command when the reader must confirm it.
- Put one action in each step.

## Notes, cautions, and warnings

- Use `> **Note:**` for information.
- Use `> **Caution:**` for a risk of data loss.
- Use `> **Warning:**` for a security risk.
- Write the risk before the action that causes it.

## Formatting

- Use sentence case for headings.
- Limit a heading to 8 words.
- Put code, paths, commands, and identifiers in backticks.
- Give each code fence a language.
- Use a table for reference data, not for an explanation.
- Use a relative link for another page in this repository.
- Use a descriptive link label.
- End each file with one newline.
- List the code paths for a page in a `ste-sources` comment.

## Notes on external names

A native agent file is a transcript. The Starforge captured form is a trace.
The GitHub import pages can name GitHub issues and pull requests. Those are
source objects, not Starforge Trails or changes.

## Check

Run the checker before you commit:

```bash
python3 scripts/ste_check.py --strict
```

Fix all errors and warnings. The checker enforces the mechanical rules.
A reviewer checks the remaining rules:

- one word for one concept.
- noun clusters of 3 words or fewer.
- correct articles.
- no omitted words.
- clear logic.
- correct technical facts.

## Maintenance

- Add a `ste-sources` comment to each page. List the code paths that the
  page documents.
- Run the checker.
- Change the page in the same commit as the code change. See
  [maintenance.md](maintenance.md).
